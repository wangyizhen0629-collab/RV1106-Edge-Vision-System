# 技术权衡分析 — Echo-Mate DeskBot

> **作者:** Wangyizhen
> **日期:** 2025-06-15
> **背景:** 嵌入式桌面 AI 机器人——设计决策、备选方案及理由

---

## 1. 概述

Echo-Mate 的每一个工程决策都面临资源受限（64 MB RAM、单核 Cortex-A7、嵌入式 Linux）与功能野心（AI 语音流水线、实时 GUI、YOLO 视觉）之间的张力。本文档梳理了关键技术权衡，说明选择了什么、放弃了什么以及为什么。

---

## 2. 权衡矩阵

### 2.1 GUI 框架: LVGL vs. Qt for Embedded

| 维度           | LVGL 9.x（选用）                   | Qt for Embedded（放弃）            |
|----------------|------------------------------------|-------------------------------------|
| RAM 占用       | ~2 MB（静态库，按需加载）           | ~15+ MB（QML + QtCore）             |
| ROM 大小       | ~500 KB 编译后                     | ~8+ MB                              |
| 渲染方式       | 自定义绘制引擎，无需 X11/Wayland    | 需要 EGLFS / Wayland                |
| UI 设计工具    | SquareLine Studio（所见即所得）     | Qt Creator / Design Studio          |
| 学习曲线       | 中等（C API，基于回调）             | 陡峭（C++ / QML / 元对象系统）       |
| 社区           | 嵌入式领域强                        | 桌面/移动端为主                     |

**决策:** 选用 LVGL——它能放入 RV1106 的 64 MB RAM 预算内，且直接通过帧缓冲渲染，无需显示服务器。代价是动画表达能力较弱、没有 CSS 式样式系统，但对于 320×240 的屏幕来说这是可接受的。

### 2.2 语音流水线: 服务器卸载 vs. 本地推理

| 维度             | 服务器卸载（选用）                  | 本地推理（放弃）                       |
|------------------|-------------------------------------|----------------------------------------|
| CPU 负载         | 极低（Opus 编码 + WS 发送）         | 沉重（ASR + TTS + LLM 推理）           |
| 模型 RAM 需求    | ~5 MB（Opus 缓冲区）                | 100+ MB（SenseVoice + CosyVoice + LLM）|
| 延迟             | 200-800 ms（网络往返）              | 500-2000 ms（在 Cortex-A7 上！）       |
| 模型质量         | 服务器端，始终最新                  | 压缩/量化，质量较低                    |
| 离线能力         | 无——需要 LAN/Wi-Fi                  | 可独立运行                            |
| 硬件 NPU 需求    | 不需要                              | NPU 对 ASR 有用，但 TTS/LLM 仍需 CPU   |

**决策:** 服务器卸载方案。RV1106 无法切实运行现代 LLM 或 TTS 模型。代价是网络依赖——机器人离线时无用。未来可考虑混合方案：本地运行 VAD + 关键词唤醒，仅将重量级推理卸载到服务器。

### 2.3 页面管理器: 自定义轻量 vs. LVGL 内置

| 维度           | lv_lib_pm（当前方案）               | lv_obj_set_tile / tabview          |
|----------------|-------------------------------------|-------------------------------------|
| 导航模型       | 基于栈的 push/pop                   | 预加载标签页，无栈                  |
| 内存占用       | 同一时刻仅一个页面在内存中           | 所有页面同时加载                    |
| 页面隔离       | init/deinit 生命周期                | 所有页面始终存活，消耗 RAM          |
| 切换控制       | 可编程，自定义动画                   | 仅限内置切换效果                    |

**决策:** `lv_lib_pm_t` 栈式管理器。在 64 MB RAM 下，同时加载全部 12+ 页面会耗尽内存。栈模型仅将活跃页面保留在内存中，以切换速度（100ms 动画 + init 时间）换取大幅降低的基线 RAM 占用。

### 2.4 字体策略: 子集 vs. 完整字符集

| 维度           | 子集方案（当前）                     | 完整 CJK 字体（放弃）              |
|----------------|-------------------------------------|-------------------------------------|
| 字体文件大小   | 每种尺寸 ~100-500 KB                | 每种尺寸 ~5-10 MB                   |
| 字形覆盖率     | 仅 UI 中使用到的字符                 | 全部 20,000+ 个 CJK 字符            |
| 风险           | 缺失字形 → 显示方框                  | 无风险                              |
| 缓解措施       | SquareLine Studio 从 UI 自动生成     | ——                                  |

**决策:** 由 SquareLine Studio 从思源黑体按需导出的字体子集。每个 `.c` 字体文件仅包含 UI 设计中实际出现的字形。这使字体总存储量控制在 1 MB 以下，而完整 CJK 字体需要约 50+ MB。代价是手写 UI 代码（如最初的番茄时钟页面）引用的字符往往不在已生成的字集中，导致显示为 tofu（方框）。缓解措施是所有页面都应通过 SquareLine Studio 设计，以便字体导出步骤自动包含所有需要的字形。

### 2.5 NPU 使用: 仅 YOLO vs. 完整 AI 流水线

| 维度           | 仅 YOLO（当前）                       | 完整流水线在 NPU 上（放弃）           |
|----------------|--------------------------------------|---------------------------------------|
| NPU 利用率     | 仅目标检测                           | ASR + 意图分类也在 NPU 上             |
| 模型兼容性     | YOLOv5 → RKNN 格式，支持良好          | ASR/TTS 模型 → RKNN：支持较差         |
| 开发工作量     | 低（瑞芯微提供 YOLO 示例）            | 极高（自定义模型移植）                |

**决策:** NPU 仅用于 YOLO 目标检测。RKNN 工具链不原生支持基于 Transformer 的 ASR/TTS 模型。移植这些模型需要在 RV1106 的小型 NPU（0.5 TOPS）上进行大量研发工作，且性能收益不确定。服务器卸载更为务实。

### 2.6 构建配置: x86 仿真 vs. 纯 ARM 开发

| 维度           | 双目标（当前）                       | 纯 ARM（放弃）                       |
|----------------|--------------------------------------|--------------------------------------|
| 开发迭代速度   | 即时（PC 上 SDL 窗口）               | 缓慢（交叉编译 + 烧录 + 启动）        |
| 硬件依赖       | GUI/UI 逻辑开发无需硬件               | 需要 RV1106 开发板                   |
| 功能覆盖       | 不含 YOLO、GPIO、摄像头              | 完整硬件访问                         |
| 调试工具       | GDB、valgrind、Address Sanitizer     | 受限（串口控制台）                   |

**决策:** 维持双目标编译。x86 仿真通过 SDL 实现快速 UI 迭代，无需实际硬件即可发现逻辑错误。ARM 交叉编译保留给硬件相关功能（GPIO、摄像头、NPU）和最终集成测试。

## 3. 风险登记表

| 风险                                | 影响程度 | 缓解措施                                      |
|-------------------------------------|----------|-----------------------------------------------|
| 服务器宕机 → 语音 AI 不可用          | 高       | 优雅降级：显示"离线"指示器                     |
| 字体字形缺失                         | 中       | 所有 UI 页面通过 SquareLine Studio 设计         |
| 页面退出时定时器泄漏                 | 高       | deinit() 中强制 lv_timer_delete——代码审查检查   |
| GPIO 冲突 (LED_BLUE)                | 低       | 文档化所有权：_maintimer_cb 拥有 LED_BLUE      |
| 高负载下内存溢出（64 MB 上限）       | 高       | 栈式页面管理器、按需字体加载                   |

## 4. 关键心得

1. **SquareLine Studio 对中文项目不可省略。** 手写 UI 代码不可避免地会引用字体子集中缺失的字符，产生 tofu 方框。WYSIWYG → 导出流水线自动包含所有引用的字形。应将其视为关键路径的一部分。

2. **服务器卸载 AI 对低端 SoC 是务实选择。** RV1106 是视觉芯片，不是 AI 推理芯片。0.5 TOPS 的 NPU 对 YOLO 绰绰有余，但对 LLM 推理差了数个数量级。接受网络依赖是正确的权衡。

3. **生命周期管理是 bug 的首要来源。** init/deinit 契约在理论上简单，在实践中却容易被违反。init() 中创建的每个定时器都必须在 deinit() 中删除。每块申请的 GPIO 都必须释放。静态分析无法捕获这些问题——只能在页面切换时进行运行时测试。

4. **函数指针表模式具有良好的可扩展性。** 注册了 12+ 页面后，`ui_apps[]` 数组仍然是页面注册的单一事实来源。新增页面是机械且可预期的流程。该模式可以扩展支持动态加载（dlopen）实现插件式页面，但对于基于 ROM 的固件模型，当前的静态注册已足够。
