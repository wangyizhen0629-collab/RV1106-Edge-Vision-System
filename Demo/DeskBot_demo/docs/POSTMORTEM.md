## 1. 项目概述

Echo-Mate 是基于 RV1106 平台构建的嵌入式桌面 AI 机器人，集成了 LVGL
图形界面、AI 语音助手、YOLO 目标检测以及 12+ 个实用应用，形成一款统一
的桌面伴侣设备。

- **代码量:** 约 [待补充] K 行（C/C++ 应用层）
- **团队规模:** 1 人（独立开发）
- **硬件目标:** 瑞芯微 RV1106，320×240 LCD，麦克风，扬声器，摄像头
- **构建目标:** x86 SDL 仿真 + ARM 交叉编译

## 2. 做得好的地方

### 2.1 双目标构建策略

x86 仿真目标极其宝贵。UI 布局、事件处理、页面切换、状态机逻辑全部可以在
PC 上利用完整工具链（IDE、GDB）进行开发和调试，无需接触硬件。仿真循环
只需数秒，而交叉编译 + 烧录 + 启动则需要数分钟。这在 GUI 开发上可能
节省了 10 倍的时间。

### 2.2 页面管理器架构

基于函数指针表注册的 `lv_lib_pm_t` 栈式页面管理器证明是一种干净、可扩展
的模式。新增页面是机械化的四步流程（创建 .h/.c、递增计数、表中注册、添加主页按钮）。
生命周期契约（init 创建、deinit 销毁）简单易懂且易于执行。12 个页面下，
数组仍然是唯一的事实来源。

### 2.3 SquareLine Studio + LVGL 集成

对于 UI 布局，SquareLine Studio 的所见即所得方法比手写 LVGL 坐标快得多。
自动的字形子集化确保 UI 中使用的每个字符都存在于生成的字体文件中——没有
缺失字形，没有 tofu 方框。导出流水线（SquareLine → C 文件 → cmake 自动包含）
是无缝衔接的。

### 2.4 AI 流水线架构（客户端/服务器分离）

将语音 AI 分离为轻量级 C++ 客户端（RV1106）和 Python 服务器（PC）在架构上
是合理的。客户端只做 Opus 编解码 + WebSocket 通信，消耗极少的 RAM 和 CPU。
所有重量级模型（SenseVoice、通义千问 LLM、CosyVoice TTS）在服务器上运行，
可以访问 GPU 加速并独立更新。

### 2.5 模块化 HAL 设计

`sys_manager`、`gpio_manager`、`event_manager` 模块提供了干净的 C API，
抽象了硬件细节。这使得应用代码可以在 x86 仿真（GPIO 函数为桩函数）和
ARM 硬件之间保持可移植，UI 代码无需修改。

## 3. 做得不好的地方

### 3.1 脱离 SquareLine Studio 手写 UI 代码

番茄时钟页面最初是手写 C 代码，直接创建 LVGL 对象。这导致了两个问题：

- **字体字形缺失（tofu 方框）：** "专注"、"暂停"、"置"等字符不在预生成的
  字体文件中，因为 SquareLine Studio 从未在 UI 设计中见过它们。现有字体
  是从其他页面的 UI 设计中生成的，仅包含它们的字符。手写页面不会触发
  字体重新生成。

- **布局尺寸错误：** 在 240px 高的屏幕上使用 180×180 的圆弧，底部没有为
  按钮留出空间；90px 的时间字体几乎和整个屏幕一样宽。没有 SquareLine
  的可视化预览，坐标计算只能手动进行，第一次就搞错了。

**教训:** 所有 UI 页面必须通过 SquareLine Studio 完成。手写 LVGL 代码仅
适用于动态元素（变化文本的标签、圆弧数值）——绝不适用于静态布局。

### 3.2 GPIO 资源冲突 (LED_BLUE)

`ui.c` 中的全局 1 秒定时器 `_maintimer_cb` 将 `LED_BLUE` 作为心跳信号
进行翻转。最初的番茄时钟设计希望在完成通知时使用 `LED_BLUE`。这造成了
无声的资源冲突——两段代码在没有任何同步机制的情况下控制同一个 GPIO。

**教训:** GPIO 所有权应在声明处文档化。共享 GPIO 需要互斥锁或单一所有者
策略。当前的处理方式（番茄时钟无 LED 通知）功能上可运行但不完整。基于
`event_manager` 发布/订阅模式的正式通知系统可以避免此类冲突。

### 3.3 没有自动化测试

项目零自动化测试——没有状态机的单元测试、没有页面切换的集成测试、没有
UI 渲染测试。所有验证都是手动的（编译、运行、点击测试）。这对长期维护
是重大风险，也错失了在项目中展示测试实践的机会。

**教训:** 至少番茄时钟的状态机和页面管理器生命周期应该有单元测试。
x86 仿真目标使自动化 UI 测试成为可能（SDL + 模拟触摸事件）。

### 3.4 嵌套 .git 目录清理问题

通过 ModelScope 下载的模型使用了 git submodule 机制，在项目树深处创建了
root 属主的 `.git` 目录。这导致父 git 仓库将这些目录视为 gitlinks（子模块），
需要手动 `sudo rm -rf` 清理数百 MB 的嵌套 `.git` 目录，之后才能正常提交。

**教训:** 大模型文件应使用独立的 `models/` 目录，并添加显式的 `.gitignore`
条目。Git submodule 或 LFS 应有意识地设置，而不是通过第三方下载脚本
意外产生。

## 4. 下次可以改进的地方

| 领域             | 当前做法                             | 改进做法                              |
|------------------|--------------------------------------|---------------------------------------|
| UI 开发          | SquareLine + 手写代码混合            | 100% SquareLine 完成所有静态页面      |
| 字体管理         | 隐式（SquareLine 生成）             | 显式字体清单 + 验证步骤               |
| GPIO 所有权      | 临时约定，无文档                     | 所有者注册表 + 编译期检查             |
| 测试             | 无                                   | 单元测试（状态机）+ 集成测试（页面切换）|
| 模型文件         | 与源文件树混在一起                   | 源码树外独立的 `models/` 目录         |
| 持续集成         | 无                                   | GitHub Actions：同时构建 x86 + ARM    |
| 错误处理         | 不一致（部分页面静默失败）           | 统一错误策略，用户可见提示            |
| 内存监控         | 无                                   | 定期堆统计日志                        |
